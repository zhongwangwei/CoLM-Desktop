# 进门向导：从一道门变成一串页

**目标**：进主界面之前，先把「这次要跑什么」问清楚 ——
空间结构、次网格方案、物理过程、土壤水力。全部选定之后再进六步主界面。

---

## 0. 为什么现在才能做

**这件事以前做不了。** 那些选择是**编译期宏**，界面上只能列出
「已经编好的内核」（`kernels/` 目录里有什么就是什么），用户选不了
一个没编过的组合。

宏改造（`docs/plan-macro-runtime.md`）把它们变成了 namelist 开关：

| 组 | 变成了什么 | commit |
|---|---|---|
| 调试三件套 | `DEF_USE_CoLMDEBUG` / `RangeCheck` / `SrfdataDiag` | `acc596a` |
| 土壤水力 | `DEF_USE_Campbell_SOIL_MODEL` | `80de820` |
| 示踪物 | `DEF_USE_TRACER` | `1a60e9d` |
| LULC 系 | `DEF_USE_LCT` / `PFT` / `PC` / `USGS` + BGC/CROP/URBAN | 进行中 |

**改造完成后一个二进制覆盖所有组合** —— 那时候向导才有东西可选。
在此之前做这个界面，只会做出一个「选了也用不了」的页面。

## 1. 顺序按约束强度排，不按「像不像一类」排

**这是这个向导最重要的一条。上一层定好，下一层的选项集合就缩小。**

先把约束的偏序理清楚（实测自 `create_defineh.bash` 模板与改造后的
`MOD_Namelist.F90`）：

```
空间结构  ─┬→ USEMPI          单点强制关
           ├→ CaMa_Flood      单点强制关
           ├→ GridRiverLakeFlow  单点/流域强制关
           └→ LATERAL_FLOW    要 CATCHMENT

次网格方案 ─┬→ BGC             要 PFT 或 PC
            └→ 站点数据要求     PFT/PC 要 pfttyp + pctpfts

土壤水力   ─┬→ TRACER          要 vanGenuchten（`MOD_Namelist.F90:1578`）
            └→ 站点数据要求     VG 要 alpha_vgm / n_vgm / theta_r

BGC        ─┬→ CROP            要 BGC
            └→ 甲烷            要 TRACER + BGC + (PFT|PC)
```

**约束是有方向的：空间结构与次网格方案在上游，物理过程在下游。**

### 所以顺序是

| 页 | 问什么 | 定了它，下一层缩紧什么 |
|---|---|---|
| **1** | 空间结构（站点/区域/全球） | 并行、河湖流、洪水这几档直接消失 |
| **2** | **研究什么过程**（水热 / 碳氮循环 / 城市 / 自定义） | 选了碳氮循环，第 3 页的 IGBP/USGS 就灰掉（BGC 要 PFT 或 PC） |
| **3** | 次网格方案（IGBP / USGS / PFT / PC） | 决定站点数据要不要 `pfttyp` + `pctpfts` |
| **4** | 土壤水力（van Genuchten / Campbell） | 决定 TRACER 能不能开；决定站点数据要不要 VG 那几个参数 |
| **5** | 其余物理开关（URBAN · TRACER · LULCC） | 被 2、3、4 共同约束，此时可选集已经确定 |
| **6** | 调试（RangeCheck · CoLMDEBUG · SrfdataDiag） | 无约束，放最后 |

### 为什么「研究什么过程」在「次网格方案」之前

**约束是双向可用的**：

```
选了 IGBP  →  BGC 不可用
选了 BGC   →  IGBP 不可用
```

同一条约束，从哪头问都能表达。**所以顺序不该由技术依赖决定，
而该由「用户先想清楚哪个」决定。**

用户先想清楚的是**「我要研究什么」** —— 水热平衡、还是碳收支、
还是城市热岛。**次网格方案是实现手段，不是研究目的。**
研究碳循环的人知道自己要碳循环，未必立刻知道那需要 PFT 方案。

**我最初把次网格排在物理过程之前，那是从技术依赖出发的排序** ——
逻辑上没错，但要求用户先回答一个他还没有依据回答的问题。

### 但「土壤水力在 TRACER 之前」那条仍然成立

土壤水力（第 4 页）约束 TRACER（第 5 页），而且**没有反向的自然问法** ——
没人会先决定「我要用示踪物」再倒推土壤水力方案。这条是单向的。

**排序的依据是：约束双向可用时按「用户先想清楚哪个」排，
单向时按依赖排。**

## 2. 常见路径不该被五页拦住

多数人跑标准配置。**第 2 页给一条捷径**：

```
第 1 页  这次跑什么       站点 / 区域 / 全球
第 2 页  关心什么过程     ┌ 水热      IGBP · van Genuchten
                          ├ 碳氮循环  PFT · BGC · CROP
                          ├ 城市      IGBP · URBAN
                          └ 自定义 → 进第 3–6 页（即上表的 2–5）
```

**四个选项都会走完后面四页**，区别只在进那几页时的初值。
预设本身是一组已经解好约束的组合 —— 它们的存在也是在说
「这三条路是走得通的」。

赶时间的人在任何一页点 **[直接开始 →]** 接受当前初值进主界面。

### 预设是「填好后面几页」，不是「跳过后面几页」

**这是这一页最要紧的一条。**

选了预设之后**仍然逐页走过** 3–6 页，只是那些页已经按预设填好了值。
用户看得到每一层选的是什么，随时能改任何一项。

| | 预设 = 跳过后续 | **预设 = 填好初值** |
|---|---|---|
| 用户看得到自己在跑什么 | ❌ 黑箱 | ✅ 逐页可见 |
| 想微调一项 | ❌ 只能选「自定义」从头来 | ✅ 走到那一页改 |
| 「默认」这个名字 | 有问题（暗示其余是偏离） | 没问题（就是一组初值） |

**所以「默认」可以叫默认** —— 它不是「正确的那个」，是「不知道从哪
开始时的起点」。用户走过四页之后，看到的是自己实际的配置，
而不是一个名字。

### 快速路径靠「跳到最后」而不是靠预设

多数人不想点四次「下一步」。给一个 **[直接开始 →]** 按钮：
接受当前所有初值，直接进主界面。

**它与「下一步」并列，不是替代** —— 想看一眼配置的人逐页走，
赶时间的人一键进去。**两条路的结果完全一样**，区别只是有没有看过
中间那几页。

## 2b. 全部列出，不可用的灰掉 —— 前提是能回去改

**做法：所有选项都摆在页面上，因上层选择而不可用的置灰。**

我一开始建议的是「只列可用的」，理由是「五页全是灰的噪音大」。
**那个担心只在用户回不去的时候成立。** 有了前进/后退按钮，
灰显是更好的选择：

| | 只列可用的 | **全列出来 + 灰掉** |
|---|---|---|
| 用户知道系统能做什么 | ❌ 看不到 | ✅ 一眼看全 |
| 知道为什么不可用 | 要读页脚 | ✅ 就在那一项旁边 |
| 知道回哪改 | ❌ 自己猜 | ✅ 提示里指明页码 |
| 噪音 | 少 | 多一点，但换来上面三条 |

### 灰选项要写两件事

```
⊘ BGC     碳氮循环
          需要 PFT 或 PC  ← 第 3 页选了 IGBP
```

**① 它需要什么** —— 让人知道这个功能的前提
**② 是哪一页的哪个选择造成的** —— 让人知道回哪改，**而且那个页码可点**

只写①的话，用户知道「BGC 要 PFT」但不知道自己在哪一步选错了；
只写②的话，用户知道回哪但不知道该改成什么。**两件都要有。**

### 底线不变

**绝不做「能点但必然失败」** —— 现有那道门的注释已经立过这条规矩：

> 没实现的那两档是 disabled，不是「点了报错」 —— 一个能点但必然
> 失败的入口比一个灰着的更糟。

置灰是**已经**符合这条的做法。要防的是另一种：让选项可点，
点完在下一页或者跑到一半才报错。

## 2b-2. 前进/后退的行为

| 按钮 | 行为 |
|---|---|
| **下一步** | 保存本页选择，进下一页。**必选项没选时禁用**（照那道门的做法） |
| **上一步** | 回上一页，**保留已选的**。改动上层选择后，下层受影响的项要重算 |
| **取消** | 回到第 1 页重来 |

**关键在「改了上层之后下层怎么办」**：

假设王五走到第 5 页，发现 BGC 灰着，点「← 第 3 页」回去把 IGBP 改成
PFT。这时第 4 页（土壤水力）的选择**应当保留** —— 它不受次网格方案
影响。而第 5 页的可选集**要重算** —— BGC 现在可选了。

**规则：回退改动只影响它下游的层，上游与无关的层保持原样。**
那正是「按约束强度排序」带来的好处 —— 依赖是单向的，重算范围明确。

## 2c. 站点数据的要求随选择变，要当场说

选了 PFT/PC 之后，站点文件要提供 `pfttyp` / `pctpfts`
（`MOD_SingleSrfdata.F90` 的 `USE_SITE_pctpfts`），而 PLUMBER2 的
站点文件**没有这两个** —— 会回落到 `<rawdata>/plant_15s/` 全球栅格。

反过来，选了 Campbell 之后，`alpha_vgm` / `n_vgm` / `theta_r`
不再需要（`mksrfdata` 里它们是 VG-gated 的）—— **要求变松了**。

**这两条都要在选的当场说**，不能等用户走到第 3 步扫站点目录时
才发现数据用不了。这正是「上一层定好、下一层缩紧」在数据这一侧的
体现：**选择不只缩紧后面的选项，也缩紧对输入数据的要求**。

## 2d. 向导的选择怎么贯穿后续全流程

**可以，而且这正是向导的价值** —— 但要先分清哪些数据受它影响。

### 一个关键区分：强迫场无关，站点数据有关

| | 受向导选择影响吗 | 为什么 |
|---|---|---|
| **强迫场** | ❌ 无关 | 八个槽位（气温/比湿/气压/降水/风×2/短波/长波）是固定的，不随 LULC 或物理方案变 |
| **站点数据** | ✅ 有关 | `IGBP_classification` / `USGS_classification` / `pfttyp`+`pctpfts` 三选一，看次网格方案；VG 那几个参数看土壤水力 |

**所以强迫场转一次到处能用，站点文件得跟着配置走。**

这条对用户体验有直接影响：他改了向导的选择重新进来，
**前处理页的强迫场产物仍然有效**（不必重转），但**站点文件可能要重建**。
界面上要说清楚这个区别，别让人以为改了配置就要从头再来一遍。

### 三层衔接，各管一段

```
向导        →  写初值到 case.nml 的 DEF_USE_*
参数页      →  可以改（那 737 个字段里就有它们）
运行时检查  →  兜底，配错了直接 CoLM_stop 并说明
```

**参数页允许改，向导只是初值设定器。** 理由：

- 那些 `DEF_USE_*` 本来就在参数页的 737 个字段里，
  强行禁止会造成「为什么这个字段是灰的」的困惑
- 专家用户可能就是要在建完算例之后微调

**但改了可能破坏依赖**（比如开了 BGC 却用着 IGBP）。那时候由第三层
兜住 —— `MOD_Namelist.F90` 里已经有那些检查了（第二、三组把编译期
`#error` 搬进去的），配错了会 `CoLM_stop` 并说明原因。

**三层各管一段，不重复也不遗漏**：向导管「常见组合一次选对」，
参数页管「专家微调」，运行时检查管「无论怎么改都不会静默跑出错结果」。

### 参数页的字段过滤要跟着改

参数页现在按内核的 `macros` 过滤：

```js
k.title = `本内核未编入（需要 ${meta?.requires?.join('、')}），设了也没用`
```

**宏消失之后这套失效** —— 第三组已经踩过（`xtask/src/usage.rs` 的
`SUBSYSTEMS` 映射让 `DEF_TRACER_*` 全被标成「本内核未编入」，
而实际上它们现在**永远可用**）。

改成按**运行时选择**过滤，措辞也要跟着变：

```
旧：本内核未编入（需要 BGC），设了也没用
新：当前配置下不生效（需要 PFT 或 PC 次网格方案）
```

**区别不只是措辞** —— 旧的意思是「你得重编内核」，新的意思是
「你改个开关就行」。那正是这次宏改造带来的变化。

### 多个算例共享一次向导

第 3 步可以一次建多个算例（批量）。**它们共享同一次向导的选择** ——
向导问的是「这次要跑什么」，不是「这个算例要跑什么」。

要给不同算例配不同物理方案的话，那是**跑两次**的事，
不是在一次向导里表达的事。

## 3. 落地时要动的地方

`domain.js` 的模块注释已经点명了关键的一条：

> **区域/全球落地时要改的是 `shell.js` 的 `STEPS`。** 它现在是模块级的
> const，被 `nextOf` / `go` / `renderSteps` 直接闭包引用 —— 三档各自一套
> 步骤链的话，得把它变成 `STEPS[state.domain]` 或一个函数，那三个调用点
> 都要跟着动。**`state.domain` 现在零读取点**，别以为它已经接好了。

向导这件事**不需要动 `STEPS`**（选完还是进同一套六步），但要：

| 改什么 | 为什么 |
|---|---|
| `domain.js` → 多页状态机 | 现在是一次性弹窗，要变成能前进/后退的向导 |
| `state.js` 加配置字段 | 选择结果要传给建算例那一步 |
| `sites.js` 建算例时写进 `case.nml` | 那些 `DEF_USE_*` 要落到算例配置里 |
| `params.js` 的字段过滤 | 参数页现在按内核的 `macros` 过滤，改成按向导的选择过滤 |

**最后一条容易漏。** 参数页现在的逻辑是：

```js
k.title = `本内核未编入（需要 ${meta?.requires?.join('、')}），设了也没用`
```

宏消失之后 `requires` 会失效（第三组已经踩过：`xtask/src/usage.rs` 的
`SUBSYSTEMS` 映射让 `DEF_TRACER_*` 全被标成「未编入」）。
**向导落地时要把这套过滤从「按编译期宏」改成「按运行时选择」。**

## 4. 分几步做

| 步 | 内容 | 前提 |
|---|---|---|
| 1 | `domain.js` 改成多页状态机（前进/后退/取消），内容先只放现有那三档 | 无 |
| 2 | 加「用哪套配置」页（默认/生化/城市/自定义） | 宏改造完成 |
| 3 | 自定义那三页 + 依赖关系的灰显与说明 | 同上 |
| 4 | 选择落到 `case.nml`，参数页的过滤改成按运行时选择 | 同上 |
| 5 | 真机验收 | 同上 |

**第 1 步现在就能做**，它不依赖宏改造 —— 把一次性弹窗改成能翻页的

---

## 5. 不做什么

- **不做「记住上次的选择」** —— 现有那道门每次启动都弹，理由是
  「它是分流点，不是一次性的欢迎页」。向导同理：**这次跑什么**
  是每次都要回答的问题
- **不在向导里选内核目录** —— 宏改造之后只有一个内核，选的是配置不是内核
- **不做区域/全球的步骤链** —— 那是 `STEPS[state.domain]` 那条线，
  与向导正交
